## 시그니처

```ts
export function runCashflow(input: CashflowInput): CashflowResult;

interface CashflowInput {
  asOf: string;              // 'YYYY-MM-DD' 기준일. 절대 Date.now() 를 쓰지 않는다
  startDate: string;         // 기간 시작
  weeks: number;             // 최대 주 수 (12/31 을 넘지 않는다)
  openingCash: number;
  warnLine: number;          // 안전선
  entityFilter: string | null;   // null = 전체 통합
  achievementRate: number;   // 0~1
  sources: { ar: boolean; won: boolean; pipe: boolean; newSales: boolean };

  receivables: Receivable[];       // 확정 채권 + 수주확정 (stage 로 구분)
  opportunities: Opportunity[];    // 파이프라인
  fixedCosts: FixedCost[];
  expenses: Expense[];
  assumptions: Assumptions;
}

interface CashflowResult {
  weeks: Period[];    // 주 단위
  months: Period[];   // 월 단위
  min: Period;        // 잔고 최저 주차
  bottom: Period | null;   // 처음으로 잔고 < 0 이 되는 주차
  shortfall: number;  // max(0, warnLine - min.cash)
  unpaid: number;     // 기간 말 미회수 이월
  totalIn: number; totalOut: number; endCash: number;
}
```

## 규칙

### R1 · 주(週) 나누기
주는 **월요일 시작**이다. 한 주가 두 달에 걸치면 **날이 더 많은 달**에 소속시킨다.
주차 번호는 그 달 기준 몇 번째 주인지로 매긴다. 기간 끝은 `min(시작 + weeks*7 - 1, 12/31)`.

### R2 · 계산 단위
실제 계산은 **주 ∩ 달력 월** 단위로 쪼개서 한다. 월 경계에서 고정비 지급일이 어긋나는 것을 막기 위해서다.
결과는 주 단위와 월 단위로 각각 다시 묶는다.

### R3 · 유입 배치
회수예정일이 **기준일보다 과거이면 기준일이 속한 칸**으로 당긴다 (이미 늦은 돈은 지금 받는다고 본다).

| 소스 | 조건 | 금액 |
|---|---|---|
| 확정 채권 | `stage='청구완료'`, `status in (open,partial)` | `amount_open` 전액 |
| 수주 확정 | `stage='청구전'` | `amount_open` 전액 |
| 파이프라인 | `stage not in (수주확정,실주,보류)` | `amount_expected × win_rate` |
| 신규매출 가정 | 월별 목표 | `(목표 − 그달 파이프라인 기대값) × 회수율`, 월말+지연일에 배치 |

### R3-b · 회수예정일이 없는 채권 ★ 회계 판단

지원사업 잔여 채권처럼 **아직 회수예정일이 잡히지 않은 돈**이 있다. 이 픽스처에서 259,759,850원이다.

**기간 마지막 칸에 몰아넣지 않는다.** 기초잔액의 3배가 되는 돈이 최저점 뒤에 들어오면
런웨이가 실제보다 안전해 보이고, 정작 "언제 들어올지 모르는 돈"이라는 사실이 화면에서 사라진다.

규칙은 둘로 나뉜다.

| 쓰임 | 금액 | 배치 |
|---|---|---|
| **연령분석** | 전액 259,759,850 | 「회수예정일 미정」 버킷. 경과일을 따지지 않는다 |
| **현금흐름** | `(잔여채권 − 계획분) × 집행률` | 가정값 `undatedAllocation` 의 월별 비율로 배분 |

현금흐름 쪽에만 집행률을 곱하는 이유는 "실제로 받을 것 같은 몫"만 넣기 위해서다.
legacy 가 이미 이 방식이다:

```
(jwAR 662,149,000 − jwPlanTax 251,277,750) × execRate 0.6759 = 277,707,878
undatedAllocation = { 9월: 0.25, 10월: 0.30, 11월: 0.25, 12월: 0.20 }
```

**두 값(259,759,850 과 277,707,878)이 다른 것은 정상이다.** 모수도 다르고 집행률 반영 여부도 다르다.
화면에는 그 이유를 문장으로 적는다. 배치된 금액은 「발생 예정·가정분」 그룹에 들어가고 가정임을 표시한다.

`undatedAllocation` 이 비어 있으면 **현금흐름에서 제외한다.** 임의의 칸에 놓지 않는다.

### R4 · 달성률과 이월
계산 단위 순서대로:
```
가용 = 그 칸의 계획액 + 이전 이월
실입금 = 가용 × 달성률
이월 = 가용 − 실입금       // 다음 칸으로 넘어간다
```
기간 말에 남은 이월이 `unpaid`.

### R5 · 이중계산 방지 — **회수월** 기준으로 맞춘다

파이프라인과 신규매출 가정을 함께 켜면 같은 매출이 두 번 잡힌다. 이때 맞춰야 하는 축은
**매출이 난 달이 아니라 현금이 들어오는 달**이다. 이중계산은 "같은 시점에 현금이 두 번 잡히는 것"이지
"같은 달에 매출이 두 번 나는 것"이 아니다.

```
파이프라인 기대값을 expected_due_on 의 월로 집계한다      → pipeByMonth
신규매출 가정 각 행의 회수일(월말 + 회수 지연일)의 월로 조회한다
차감액 = pipeByMonth[그 회수월] / 회수율
순목표 = max(0, 월 목표 − 차감액)
배치액 = 순목표 × 회수율 × 법인 배분
```

회수율로 나눈 뒤 다시 곱하므로 순효과는 정확히 기대값만큼 차감이다.

**매출월로 매칭하면 안 된다.** 이 픽스처에서 그 차이가 그대로 드러난다:

| | 8월분 | 9월분 | 10월분 | 11월분 | 12월분 |
|---|---|---|---|---|---|
| 회수일 | 10/15 | 11/14 | 12/15 | 2027-01-14 | 2027-02-14 |
| 기간 내 | ✓ | ✓ | ✓ | ✗ | ✗ |

파이프라인은 11월(96,000,000) · 12월(42,500,000)에 걸려 있다.
**매출월**로 맞추면 11월분·12월분 행을 찾는데 둘 다 기간 밖이라 배치되지 않아 **차감이 통째로 사라진다**.
**회수월**로 맞추면 11월 → 9월분(배치됨), 12월 → 10월분(배치됨)에 정확히 걸려 138,500,000이 다 빠진다.

**잔여분 처리 (fallback)**: 파이프라인 회수월에 대응하는 신규매출 행이 아예 없으면 그만큼 차감이 남는다.
남은 몫은 **배치되는 달 중 이른 순서대로** 떠넘긴다. 잔고 최저점이 더 일찍·더 낮게 나오는 쪽이
안전한 오차이기 때문이다. **차감이 사라지게 두는 것만은 안 된다** — 그건 이중계산을 남기는 것이다.
(이 픽스처에서는 회수월 매칭만으로 전부 소진되어 fallback 이 발동하지 않는다.)

### R6 · 지출 배치

> **`Expense.on` 은 쓰지 않는다.** legacy 가 `{on:true}` 를 붙여 두지만 `run()` 이 한 번도 읽지 않는
> 죽은 필드다. 집행 여부는 전적으로 `exec_state` 가 결정한다. 타입에서 아예 제거한다.

- **고정비**: 매달 지급일에. 법인 필터가 걸리면 배분 비율을 곱한다. 지급일이 그 달 말일보다 크면 말일로.
- **일회성**: 집행상태에 따라
  - `집행` → 그 칸에 그대로
  - `연기` → 지정 주차, 없으면 기본 주수만큼 뒤로. 기간 밖이면 연내 미집행으로 빼고 기록만 남긴다
  - `취소` → 계산에서 제외, 기록만 남긴다

### R7 · 잔고 누적
```
칸.기말 = 칸.기초 + 실입금 − (고정비 + 일회성)
다음 칸.기초 = 이번 칸.기말
```

### R8 · 연령분석 (별도 함수)
`ageReceivables(receivables, asOf)` — **잔액을 나눈다. 매출액을 나누지 않는다.**

버킷 경계는 **경과일 `d = asOf − due_on` 기준, 상한 포함(`<=`)** 으로 확정한다:

| 버킷 | 조건 |
|---|---|
| 정상 | `d <= 0` (당일 포함) |
| 30일 경과 | `1 <= d <= 30` |
| 60일 경과 | `31 <= d <= 60` |
| 90일 경과 | `61 <= d <= 90` |
| 90일 초과 | `d >= 91` |
| 회수예정일 미정 | `due_on` 이 없음 |
`stage='청구전'`은 연령분석에서 제외한다 (청구도 안 한 건에 연체는 의미가 없다).
**6개 버킷 합계 = 매출채권 총액**이어야 한다. 어긋나면 테스트 실패.

## legacy 대조 — 정확 일치

`legacy/index.html` 의 `run()` 도 정수 원으로 바꿨다(rev.4). 금액을 곱해 쪼개는 곳은
조각마다 반올림하지 않고 **누적합을 반올림**한다 — 조각의 합이 정확히 원금이 되고 잔고가 밀리지 않는다.

바꾼 곳은 다섯 군데다.

| 위치 | 무엇을 |
|---|---|
| 지원사업 잔여 채권 | 총액을 정수로 끊고, 월·법인 배분을 누적 반올림으로 쪼갠다 |
| 신규매출 가정 | 회수액을 정수로 끊고, 법인 배분(0.2/0.8)을 누적 반올림으로 쪼갠다 |
| 달성률·이월 | 점화식은 정확히 굴리고, 누적 실입금을 반올림해 그 차이를 각 칸의 실입금으로 |
| 고정비 법인 배분 | 배분액을 정수로 |
| 공용 헬퍼 | `wonI()` · `splitByRatio()` 추가 (엔진의 `money.ts` 와 같은 규칙) |

그 결과 **주별·월별·합계 전부 원 단위까지 일치**한다. 1원이라도 어긋나면 `legacy-parity.test.ts` 가 실패한다.
